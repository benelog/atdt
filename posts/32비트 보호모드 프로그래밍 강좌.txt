
 제  목 : [9503](1)32비트 보호 모드 프로그래밍
  "프로그램의 처리속도가 2배로 향상되고, 메모리의 640K 한계는 사라
진다." 보호 모드 프로그래밍에서 제시하는 장점들이다. 많은 프로그래
머들이 힘겨운 싸움을 해 오던 것들이 쉽게 해결되는 보호 모드 프로그
래밍이 널리 쓰이지 않는  이유는 이에 대한 자료가 부족했기 때문이었
다. 본 연재에서는  보호 모드 프로그래밍을 이론만으로 소개하는데 그
치지 않고 보호 모드를 이용한 프로그래밍을 완성할 것이다. 첫회로 보
호 모드 프로그래밍의 이해와 이를 위한 준비사항들을 점검해 본다

  ● 글 \ 정 재 욱, 박 영 길, 김 해 성 (한양대 전자계산학과)
  연 재
1. 32bit 보호 모드 설명과 컴파일러 비교설명
2. 보호 모드 프로그래밍 1 슈퍼 VGA 인식루틴과 마우스 처리
3. 보호 모드 프로그래밍 2 입출력 한글 작성 루틴
4. 보호 모드 프로그래밍 3 PCX & GIF 등의 이미지 작성5. 보호 모드 프로
그래밍 4 데모 프로그램

 [개요]
  OS/2 Warp 3.0과 윈도우즈 95가 나오는 마당에 도스 프로그래밍이 웬
말이냐 할 지도 모르겠지만, 여기서 소개하려고 하는 보호 모드 프로그
래밍은 기존의 640KB를  뛰어넘어 386고유 기능들을 사용함으로써 도스
기반의 16비트  프로그래밍 기법을  뛰어넘을  수 있는 혁신적인  방법
이
다. 따라서 도스  프로그래밍을 고집하는 사용자들을 위하여 이에 대해
소개하고자 한다. 현재 우리가 사용하고 있는 컴퓨터를 보면 거의 모두
386이상의 기종이 주를 이루고  있다. 그러나 그러한 컴퓨터의 모든 기
능을 사용할 수  있는 프로그램은 드물다. 대부분의 프로그램들이 8086
을 기준으로 작성되기  때문에 프로그램들이 80286이상에서 실행된다면
단지 좀더 빠른 8086(XT)을  사용하고 있는 것이 된다. 요즘 들어 시스
템의 메모리를  조금이라도 더  사용하기  위하여 XMS나 EMS를  사용하
는 프로그램들이  나오고 있긴 하지만 그런 프로그램을 작성하는  것은
여간 번거로운 것이 아니다. 그러면  이제 이러한 것을 극복할 수 있는
보호 모드에 관하여 알아보기로 하자.
  80286이후의 마이크로프로세서 (CPU)는 두 가지 모드 즉, 실제 모드
와 보호 모드를 지원하게 되는데(엄밀히 말하면 80386이상에서는 가상
8086모드도 있으며 이것은 실제 모드와 거의 유사하다. 그러므로 여기
서는 실제 모드와 동일하게 취급한다. 일반적으로 메모리 관리자를 사
용하면 가상 8086모드에서 CPU가 동작하게 된다. 예를 들면 윈도우즈의
도스 세션 등이 바로 그  예이며, 여러 개의 가상 모드를 생성할 수 있
으므로 도스 멀티태스킹이 가능하다), 프로그램이 실제 모드와 보호 모
드로 구분되어 실행된다는 것을  아는 사람은 그리 많지 않다. 물론 프
로그램에 따라 실제 모드와 보호 모드를 병행하면서 실행되는 프로그램
도 있으나 일반적으로 육모드로 만들어 둔 것이다.
  그래서 특별히 사용자의 요청이 없으면 8086프로세서 호환 상태인 실
제 모드로 진입하게  되는 것이고, 윈도우즈나 OS/2와 같은 운영체제들
은 보호 모드를 사용하게  되는 것이다. 자 이제 차근차근히 실제 모드
와 보호 모드에 대해서 알아보기로 하자.

  실제 모드
  실제 모드란 간략하게 설명을  해 보면 단지 빠른 8086(과거 XT에 탑
재)으로 인식을 하면 된다. 즉,  8086과 거의 다른 점이 없다. 실제 모
드는 원래 8086마이크로프로세서와 호환성이 있으며 응용 프로그램이 1
메가 바이트의 메모리까지 사용할  수 있다. 실행상에 좀 더 편해진 것
은 이들  상위 기종에서는 8086과 달리  좀 더 많은 레지스터를  사용할
수 있다는  것이다. 그리고 명령어들이 조금  더 추가되어 졌다는  것이
다. 그래서 하위 기종에서 실행이 되는 프로그램들이 이러한 상위 기종
에서도 실행되는 것이다.  컴퓨터들이 기본적으로 4MB 이상의 메모리를
기본으로 장착하고 있는 요즈음  도스 메모리 내에서 점점 크기가 커진
프로그램들을 작성하고 실행시키는  것은 정말로 힘든 일이다. 특히 그
래픽 프로그램이나 데이터베이스  프로그램 같이 많은 메모리를 필요로
하는 프로그램의 경우 더욱 많은 메모리의 필요성을 실감하게 된다. 그
래픽 프로그램의  경우 256색의 640*480의  화면을 저장하려면  300KB의
메모리를 소요한다. 그러나  그런 그림이 여러 장이 되거나 32,000색이
나 1,600만 색으로 될 경우 그 필요한 메모리 양은 640KB를 넘어 수 MB
가 필요하게 된다. 그렇다고  하드로 저장을 하여 사용을 할 경우 많은
어려움과 시간이 걸리게 된다. 물론 XMS나 EMS를 사용하여 저장을 할수
도 있다. 그러나 기본 메모리를 사용하는 프로그램에 비하여 많은 어
려움과 프로그램의 실행시 메모리 관리자가 꼭 필요하고 그 특성이 맞
아야 한다. 그리고 80386기종 이상에서는 비록 컴퓨터가 32비트라도 16
비트 처리를 하기 때문에 속도 역시 문제가 된다.

  보호 모드
  시스템의 모든 기능을 사용할 수 있는 모드가 보호 모드이다. 일단보
호 모드의 장점들을 구체적으로 열거해 보면 아래와 같다.

  1. 32비트 처리가 줄 수 있는 첫 번째 장점은 속도의 증가이다. 보통
    1.5~3배정도 차이가 난다고 보면 된다.
  2. 기존의 세그먼트 방식에서 벗어남으로써 배열 등을 64K 이상 잡아
    도 아무런 문제가 없다.
  3. 프로그램 코드나 데이터에 대한 보호가 가능하며 치명적인 에러에
    대해 대비할 수가  있다. 최소한 실제 모드에서 프로그램 시스템이
    불안정하다는 경고와 함께 도스 모드로 빠져나오게 된다.
  4. 이밖에도 실제 모드에서는 거의 불가능한 멀티태스킹 프로그램 작
    성이 가능하다.

  결국 보호 모드 하에서는  위에 언급했던 속도와 메모리에 관한 어려
움이 많이 극복될 수 있다.


  보호 모드의 주소 참조
  보호 모드에서는 메모리 관리와 가상 메모리 관리, 페이징, 프로텍션
(프로그램들 간의 보호),  다중 작업(MultiTasking)을 지원하기 위하여
마이크로프로세서가 진보된 구조를 가지게 된다. 여기서는 일반적인 32
비트 프로그램에 중점을 두고  주소 참조에 대한 사항만 간단히 설명을
하고 넘어가기로 하자. 보호 모드에서는 8086과는 달리 80286에서 16MB
까지, 80386, 80486과  펜티엄에서는 4GB까지 직접 메모리 접근이 가능
하다.(따라서 Far 호출이 없어지게 되며 단지 Near 선언으로 접근이 가
능하게 된다) 실제 모드와 보호 모드의 주된 차이점은 프로세서가 논리
주소를 물리 주소로  바꾸는 방법에 기인한다. 프로세서가 메모리를 억
세스할 때마다 명령어와 자료를  읽어 오거나 저장하기 위해 논리 주소
로부터 물리 주소를  생성한다. 논리 주소는 응용 프로그램이 사용하는
주소이고, 물리 주소는 시스템 메모리의 실제 주소이다.

  실제 모드의 주소 참조
  실제 모드에서 하나의  논리 주소는 16비트 셀렉터(세그먼트 주소)와
하나의 16비트 오프셋으로  구성된 32비트 값이다. 물리 주소는 프로세
서가 시스템에서 데이터와  메모리 요소를 바꿀 때 사용하는 주소이다.
실제 모드에서 하나의 물리  주소는 20비트 값이다. 반면에 80286 보호
모드에서는 물리 주소는  24비트(16MB) 값이고 80386이상의 기종에서는
32비트 오프셋과 더불어  다시 32비트(4GB)이다. 실제 모드에서,  물리
주소의 생성은 간단히  세그먼트 주소를 왼쪽으로 4비트 이동시킨 다음
(16을 곱함)오프셋을 더함으로써  가능하다. 그러므로 생성된 20비트는
아래의 그림 1처럼  메모리를 억세스 하는데 사용된다. 역시 80386이상
의 기종의 실제 모드도 그림과 같이 동작한다.

  보호 모드의 주소 참조
  보호 모드의 주소 생성 방식을 알기 위하여 먼저 보호 모드의 일반적
인 구조체에 관하여  알아보자. 보호 모드에서는 먼저 디스크립터 테이
블(Descriptor Table)이라는 것이  사용된다. 물론 이 디스크립터를 가
리키는 레지스터도 존재한다. 일반적인 디스크립터들을 보면 아래와 같
은 구조를  가지는데 Base 주소는  물리적인 메모리의 위치를  가리키고
Limit는 할당된 양을 가리킨다.  그리고 앞쪽의 비트는 그 할당된 메모
리의 정보를 포함한다.  286에서는 Base 주소가 24비트로 16MB까지 386
이상에서는 32비트로 4GB까지 가리킬 수 있다.

             1MB +----------------+
     Offset-+    +----------------+
            +----+->              | 64KB
  Selector x 16 -+----------------+                 | Address Space  |
               0 +----------------+
     그림1 실제 모드 물리 주소 생성

  그리고 Limit는 286의  경우는 16비트로 64KB까지 386의 경우에는 20
비트로 구성이 되어진다.  아래의 그림은 8바이트를 가지는 386의 디스
크립터를 나타낸다. 일반  디스크립터는 아래에 다시 설명을 하고 먼저
보호 모드에서 사용되는 디스크립터들을 포함하는 디스크립터 테이블에
관하여 알아보자.  아래의 내용은 다분히  개념적이고 이해하기  어려운
내용들이므로 초보자들에겐 부담이 갈지 모른다. 하지만 적어도 전산을
전공하는 학생들에겐 필히 알아두고 활용해야 될 내용이라고 생각한다.
그럼 건투를 빌며  계속 서술해 나가겠다. 일반적인 디스크립터에 대한
구조는 다음과 같다. 총 8바이트로 이루어져 있다.
          일반적 디스크립터(Descriptor) - 64비트(8바이트)
   63  -  52      51  -  20    19  -  0
+--------------+--------------+---------+
|  접근정보    | 주소         |양(Limit)|
|(Access Right)|(Base Address)|         |
+--------------+--------------+---------+
  보호 모드에는 다음와  같은 GDT, LDT, IDT같은 디스크립터 테이블들
이 존재한다. 각각 이들에 관하여 알아보면

  GDTR(Global Descriptor Table Register)
  -> GDT(Global Descriptor Table)
  IDTR(Interrupt Descriptor Table Register)
  -> IDT(Interrupt Descriptor Table)
  LDTR(Local Descriptor Table Register)  -> LDT(Local Descriptor Table)

  먼저 GDT는 8바이트로  이루어진 디스크립터들의 집합체이다. 이 GDT
는 시스템에서 사용하는 가장 기본적인 전역 디스크립터 테이블이다.이
것은 가리키는 레지스터로 GDTR이 있다. 이 GDTR은 총 48비트로 아래와
같은 구조를 가진다. 286의 경우는 Base가 24비트이다. GDT는 메모리에
연속적으로 8바이트의 배열의 형태로 존재한다.

    47 - 40     39 - 16   15 - 0
  +----------------------+------+
  |BASE(31-24) BASE(23-0)|LIMIT |
  +----------------------+------+

  이 GDT는  항상 메모리내에 상주를  하는데 즉, 앞의  BASE(32비트)로
4GB이내의 어느 위치를 가리키고  뒤의 LIMIT로  그 한계 즉, 할당량을
가리킨다. LIMIT는 16비트로 0  ~ 64KB-1까지 나타낼 수 있다. 결국 하
나의 디스크립터가 8바이트이므로 GDT내에 최대 8192개의 디스크립터가
존재할 수 있다. 이 GDT내의 디스크립터들은 다중 작업(Multi-Tasking)
의 경우 여러 프로그램에서 같이 사용을 할 수 있다. 이 GDT내에는 LDT
의 디스크립터와  다중 작업의 각  작업(Task)의 정보를 담은  TSS(Task
State Segment)의 디스크립터와  일반적인 공유 메모리의 디스크립터를
가진다. 즉, 다중 작업의  경우 GDT를 통하여 여러 작업을 관리하게 된
다. IDT는 일반적인 디스크립터처럼 세그먼트의 정보를 가지는 것이 아
니라 마이크로프로세서  (CPU)가 인터럽트나 예외상황(Exception) 발생
시 호출하는 프로그램(Service  Routine)의 디스크립터를 저장한다. 이
것을 가리키기 위하여  IDTR이 있으며 역시 48비트로 GDTR과 비슷하다.
그러나 386의  경우 단지 256개의  인터럽트와 예외 처리를  지원하므로
256개 이상 지원하도록  설정되지 말아야 한다. IDT내의 각 디스크립터
는 Interrupt Gate라고  불리고 이들은 인터럽트에 대한 서비스 루틴의
시작 주소를 가리킨다. 각  Gate는 8바이트로 속성과 서비스 루틴의 시
작 주소를 포함한다.
  LDT 역시  메모리 지원을 위하여  사용되어지는데 각각의  프로그램은
GDT 이외에 자신의 디스크립터  테이블을 사용할 수가 있다. 이러한 자
신의 디스크립터 테이블을  LDT(Local Descriptor Table)라 부른다. 이
디스크립터 테이블에는  그 작업(프로그램)이  사용하는 메모리  공간을
정의한다. 이 LDT내에는 각 할당된 세그먼트의 정보를 가지는 디스크립
터들이 존재한다.
  각 디스크립터들은 위에서  설명한 일반 디스크립터들로 세그먼트 디
스크립터라고 한다.  이런 세그먼트  디스크립터는 8바이트로  메모리의
위치(4바이트-32비트:4G까지 어드레싱)와  그 할당량(20비트: 1MB-앞의
정보에 의하여 조각 단위가 1Byte 또는 4KB가 될 수 있다. 그러므로 최
대 4GB까지 Limit를 정할 수 있다.) 그리고 그 세그먼트의 정보(접근권
한)를 포함한다

  각각의 디스크립터는 CODE(실행코드 블럭), DATA(자료 블럭), 스택등
등을 가리키는 정보를 포함한다.  다중 작업시 각 프로그램의 LDT를 가
리키는 디스크립터는 GDT에  저장되어 있어서 프로그램이 바뀔 때 이것
역시 바뀌어 다른 LDT를 가지므로 각 프로그램이 서로 다른 프로그램의
영역을 침입하지 못하도록 시스템에서  방지할 수 있다. 그럼 LDT를 가
리키는 역할을 하는  LDTR에 대해서 알아보기로 하자. LDTR은 16비트로
이루어져 있다. 그러므로  LDTR 스스로는 GDTR같이 메모리의 어느한 세
그먼트를 가리킬 수가 없다.  그리하여 이 LDTR은 48비트의 Cache가 함
께 작용을  한다. LDTR은 GDT내의  어느 하나의 디스크립터를  가리키는
셀렉터(Selector)의 구실을 하고 LDTR이 가리키는 디스크립터의 내용이
다시 LDTR  Cache로 복사되어 이  Cache에 의하여 LDT를  가리키게된다.
여기서 Limit는  다시 16비트로 GDTR과  같다. 그러므로 최대  4096개
의 디스크립터를 가질 수 있다.

립터와 셀렉터에 관하여  알아보기로 하자. 보호 모드에서 물리 주소를
생성하려면 논리 주소의 셀렉터(세그먼트) 부분이 디스크립터 테이블에
대한 인덱스로  사용되어 진다. 즉,  세그먼트 레지스터의 값에  의하여
직접 물리적 주소의 위치를 알 수 있는 것이 아니라, 세그먼트 값은 단
지 메모리의 위치와 양 그리고 속성을 담은 디스크립터를 모아 놓은 디
스크립터 테이블의 하나를 가리키는  셀렉터 역할을 한다. 즉, 보호 모
드에서 세그먼트 레지스터는 셀렉터로 사용된다고 보면 된다. 디스크립
터 테이블  내의 엔트리는  논리 주소들의 오프셋  부분에 대한  32비트
(286에서는 24비트) 베이스 주소이며 다음의 그림 2와 같이 물리주소를
생성한다. 메모리를  가리키기 위해서는 실제  모드와 같이  세그먼트와
오프셋만으로 위치와 그 양을 알 수가 없다. 그러므로 디스크립터를 사용
하여 메모리의 위치와 양 그리고 속성을 지정할 수 있는데 그러한 디
스크립터는 LDT나 GDT내에 생성이 된다. 이렇게 디스크립터들로 이루어
진 메모리 세그먼트들을 사용할 때 그 범위를 넘거나 사용 권한이 없거
나  또는 읽기  전용의 메모리에  쓰는 경우  예외 상황인  GeneralProt
ection Fault가 발생을  하여 다중 작업의 경우 프로그램간의 메모리를
보호하여 줄 수   있다. 여기서 예외(Exception) 상황은 실제 모드에서
숫자를 0으로 나누었을 경우처럼 에러의 발생과 같이 메모리를 잘못 사
용할  경우에도 발생하게  된다. 이들  셀렉터들을  보면 역시  Segment
Descriptor Cache Register(8바이트)와  짝을 이루어 동작을 한다.아래
의 도표에서 세그먼트 레지스터 6개가 존재하므로 사용할 수 있는 최대
셀렉터로는 6개 까지이다.  즉, 실제 모드 프로그램에서 한순간 가리킬
수 있는 세그먼트가   보통 4개(386 실제 모드에서는 6개)이듯이, 보호
모드 역시 6개의 디스크립터를 가리킬 수 있다.

  보호 모드하의 가상 메모리 관리
  실제 모드에서 논리  주소가 주어졌을 때, 응용 프로그램은 대응되는
물리 주소를 결정할 수 있다. 대개 이런 것이 보호 모드에서는 논리 주
소의 셀렉터의 부분이 디스크립터 테이블에 대한 인덱스이므로 직접 물
리 주소를 가리킬 수 없게 된다. 즉, 셀렉터 그 자체는 물리 주소 계산
에 직접적인 관계가 없게  된다. 이런 것이 가상 메모리 관리에서 응용
프로그램에 영향을 주지 않고 구현될 수 있는 이점이다. 예를 들면, 단
지 세그먼트의 디스크립터의 베이스 주소 부분을 새롭게 함으로써 운영
체제가 세그먼트를  사용하는 응용 프로그램에  영향을 주지 않고  물리
메모리 주위의 세그먼트로 옮길 수 있다. LDT나 GDT의 디스크립터를 바
꾸어 놓고 메모리의 내용을 옮기므로 응용 프로그램은 단지 세그먼트의
셀렉터를 참조하게 되므로  응용 프로그램 내의 셀렉터는 디스크립터의
변화에 영향을 받지  않는다. 이들 셀렉터의 비트   중 하위  3비트 중
0, 1비트는 이 셀렉터의 Request Privilege Level을 가리키고 2번 비트
는 이 셀렉터의 디스크립터가 GDT에 존재하는지 LDT에 존재하는지를 결
정한다. 그러므로  남은 13비트와 2번  비트를 합쳐 14비트를  형성하고
Offset 32비트와  합쳐 주소를 생성하여  결국 64TB(286에 서는  1GB)의
가상 메모리를 생성할  수 있다. 응용 프로그램은 거의 디스크립터들을
다룰 필요가 없다. 즉,  운영 체제나 메모리 관리자가 디스크립터가 필
요할 때 생성하고 제거하므로 응용 프로그램에서는 단지 셀렉터만 알면
된다. 셀렉터는 파일핸들과 비슷하다. 추가적인 정보를 가지고 있는 디
스크립터 테이블에 대한 인덱스로써 작용한다. 32비트 응용 프로그램은
32비트 주소 공간의 FLAT(플래트) 메모리 모델을 사용하기 때문에 셀렉
터를 거의 다룰 필요가 없다.

  도스 확장자
  도스상에서 보호 모드를 직접 이용하는 프로그램을 작성하는 것은 매
우 어렵다. 보호  모드를 직접 이용하는 프로그램을 작성하기 위하여서
는 우선 어셈블리어를 사용해야 하고 보호 모드의 모든 처리 부분을 사
용자가 직접  작성하여 주어야 한다. 특별한  기능을 하는 OS나  메모리
관리자가 아니고는 일반적인  프로그램을 작성하기 위해서는 이러한 모
험(직접작성에 의한 버그 등등)을 할 필요가 없다. 우리가 보호 모드용
프로그램을 작성하려는 목적이 빠른 처리 속도와 시스템의 메모리 그리
고 부분적인 병렬 처리 때문이라면 이러한 수고를 덜 수 있다. 그 방법
이  도스 확장자를  이용하는  방법이다.  물론 윈도우즈  도스세션이나
OS/2, 윈도우즈 NT하에서는  이러한 보호 모드 인터페이스가 제공이 되
지만 도스에서는 직접적으로  제공되지 않는다. 그러면 이제 이러한 확
장자에 관하여 알아보자.

  보호 모드 규약(VCPI, DPMI)
  VCPI(Virtual Control Program Interface) 규약은 1987년 Phar-Lap과
Quarterdeck에 의하여 처음  설계되었다. 처음 이들은 자체적으로 제작
하여 서로 호환되지 않았다. 점점 문제가 많아지게 되자 이들이 호환성
을 위하여 만든 규약이  VCPI다. 이 VCPI는 EMS 에뮬레이터와 확장자의
충돌을 제거할 목적으로 작성이  되었다. 즉, VCPI는 보호 모드와 가상
86모드의 전환과 메모리 관리 기능을 제공할 목적으로 충실하게 설계되
었다. 그러나 그후 많은 회사들이 확장자에 관심을 가지고 참여하게 되
었고 결국 1989년엔 보다 안정적인 VCPI 설계 명세서를 발표하였다. 이
렇게 형성된 협의회에는 위의  두 회사뿐 아니라 에르고, 로터스, 쿼드
램, 레셔날 시스템  등도 참여했다. 오늘날의 EMS 에뮬레이터와 도스확
장자는 이러한 표준하에서 작성된 것들이다.
  또, 다른 규약인 DPMI(Dos  Protected Mode  Interface)는 원래 윈도
우즈 개발에 포함된  인터페이스 규약으로 처음에는 윈도우즈만이 이것
을 지원하였으나 마이크로소프트의  홍보와 노력으로 요즘은 거의 표준
형태로 자리잡게 되었고 결국  많은 회사가 이 규약을 지원하기에 이르
렀다. 결과적으로 따져봤을 때  비록 VCPI가 먼저 생긴 보호 모드 규약
이긴 하지만 DPMI가 VCPI를 누르고 현 업계의 표준으로 자리를 잡게 된
것은 VCPI가 80286에서 사용을 할 수 없었고 또 보호 모드의 고급 기능
을 사용할 수가 없었기 때문이다. 물론 이후 확장된 형태인 XVCPI가 발
표되었지만 윈도우즈  강세와 마이크로소프트의  노력으로 DMPI가  현재
보호 모드 시장을 주도하고 있다. 그리고 많은 회사가 도스 확장자 SDK
라는 이름으로 프로그램을  판매하고 있는데, 이러한 도스 확장자를 사
용하는 프로그램들은 메모리를  많이 필요로 하는 프로그램들로 그래픽
이나 오락 프로그램들이 대부분이다.

  컴파일러와 도스 확장자
  일반적인 보호 모드 프로그램들은 32비트를 사용하기 때문에 386이상
에서만 실행된다. 보호 모드는  현재 16비트와 32비트 두 가지가 있다.
16비트는 80286에서  32비트는 80386이상의  CPU에서 동작한다. 그리고
16비트의 경우 메모리는  16MB까지, 32비트는 4GB까지 사용할 수 있다.
물론 가상 메모리를 사용하여  그 이상을 사용할 수도 있다. 16비트 보

었다. 하지만 라이너  쉬네커라는 독일 프로그래머가 DPMI와 VCPI를 동

1. 초기화 파트
  간단히 말하면 이 부분은  실제 모드에서 보호 모드로 진입하기 위한
단계이다. 잠시 아랫부분을  읽지 말고 어떠한 동작이 필요하겠는지 생
각해 보도록 하자. 생각이  끝났으면 필자가 쓴 것과 비교를 해 보도록
하자.

첫 번째,
  일단 현재  모드가  보호 모드인지  실제 모드인지 알아내야 할  것이
다. VCPI  호스트가 있는지  아니면  DPMI 호스트가 있는지를  알아내야
하기 때문이다. 왜냐하면 서로 다른 호스트가 있다면 보호 모드로 진입
하기 위한 루틴이  틀려지기 때문이다. 보통 VCPI는 EMM386이나 QEMM과
같은 확장(Expand) 메모리 관리자 등이 지원하고 DPMI는 윈도우즈의 도
스창 또는 쿼터덱의 QDPMI 등이 지원한다.

두 번째,
  중요한 부분이  있는데 그것은 바로  실제 모드의 인터럽트  벡터들이
함부로 사용되지 못하도록 각 인터럽트들을 재배치하는 일이다. 이것은
프로그램상에서 예기치 않은 인터럽트가 발생했을 때 보호 모드 인터럽
트 루틴으로 제어를 옮겨서 시스템을 보호할 수 있도록 하기 위한 것이
다.

세 번째,  각종 디스크립터들(GDL,  LDT, IDT)을 할당하고  초기화 하는
 부분이다. 보호  모드에서 전체적인 메모리를  관리하기 위해서  디스크립터를
이용하게 되는데, 이 부분을 초기화 해야 각 디스크립터들은 메모리 영
역에 맞게 할당이 될 수 있다.

네 번째,
  보호 모드로 진입하기 위한 루틴 실행 그럼 이제 간단한 코드들로 위
의 순서들을 표현해 보겠다.
    : (각종 선언부)
#define NO_SERVER  0
#define DPMI       1
#define VCPI       2
    : (각종 함수부)
void initialize_dos_extender()
{
   int mode = check_mode();
   // 1.현재 어느 모드에 있는지 검사하고 mode 변수에
   // 값을 되돌림
   if ( (mode == REAL_MODE) || (mode==V86MODE) )
   // 현상태가 실제 모드 또는 가상 8086모드라면
   // 보호 모드에 진입하기 위한 루틴을 실행해야 함
   // 따라서 현상태가 보호 모드인 경우엔 아래의
   // 루틴들을 다시 실행시켜야 할 이유가 없다.
   {
   // 2. 도스 인터럽트 벡터들을 다시 재배치시키는
   // 루틴들을 실행해야 한다.
      reallocate_dos_interrupts();   // 3. LDT, IDT, GDT 등의 디스크립터 테이블
을
   // 설정하고 초기화 시켜야 한다.
      initialize_descriptor_tables();
   // 4. 이제 보호 모드로 진입하기 위한 루틴들이다.
      switch ( check_host() )
      {
         case DPMI   :
         // DPMI 호스트가 존재하면 DPMI함수 1687H를 호출
                  call_dpmi_function();
                  break;
         case VCPI   :
         // VCPI 호스트가 존재하면 함수 DE0CH를 호출
                  call_vcpi_function();
                  break;         case NO_SERVER:
         // CR0 레지스터의 PE비트를 1로 셋팅함
                  call_PEbit_enable();
                  break;
         default :
                  printf("###Error### Impossible event!!!\n");
                  break;
      } // e-switch
   } //e-if
} //e-initialize_dos_extender()

  2. 로더 파트
  도스 확장자의 로더   파트는 보호 모드용 프로그램을 알맞은 형식으
로 메모리에 읽어들인다. 보통의  EXE 파일과는 다르게 보호 모드용 프
로그램은 다른 형식으로  구성되는데, 보통 보호 모드용 프로그램 등은
윈도우즈나 OS/2의 실행파일과  같은 구조로 되어 있다.이에 도스 확장
자는 프로그램의 메모리 모델과 실행 형식에 맞게 프로그램을 메모리에
읽어들여 실행 준비를 한다.
3. 보호 모드 인터럽트 처리 파트
  이 파트는 도스에서 발생한 인터럽트들을 보호 모드에 맞게 처리하는
부분이다. 보통 인터럽트라고 하면 세 가지의 경우를 말하는데, 하드웨
어 인터럽트, 소프트웨어  인터럽트, 프로세서 내부 인터럽트로 나뉘어
진다. 해당하는 경우를 예시해 보면 아래와 같다.

하드웨어 인터럽트  - 키보드, 마우스 등과 같이 주변기기 등에서 발생하는 것들
소프트웨어 인터럽트
  - 시스템 호출
프로세서 내부 인터럽트
  - Divide Error(0으로 나눗셈), Overflow,
    Single Step(한 단계씩 실행),
    Breakpoint(포인트까지 실행)

  따라서 위의 인터럽트에   해당하는 모든 부분을 도스 확장자가 처리
할 수 있어야 예기치  못한 상황들에 대비할 수가 있다. 그리고 도스와
호환성 문제도 생기지 않게 된다.

4. 실제 모드 인터럽트 처리 파트
  이 부분은 보호  모드에서 실제  모드 인터럽트가 발생했을 때  이에
맞게 처리할 수 있어야 한다. 어떻게 보면 오버 헤드라고 볼 수도 있지
만 호환성을 위해선 꼭  필요한 루틴이라 할 수 있겠다. 간단히 말하면
실제 모드 인터럽트를 보호 모드에서 흉내(emulate)낸다고 봐도 무방하
다.

5. DPMI와 VCPI 등과의 인터페이스 부분
  만약에 DPMI나 VCPI를 사용하는 서버가 존재한다면 도스 확장자는 그
서버들을 최대한  이용해서 각 기능들을  사용하는 방법을 채택하고  있
다. 최근  들어 윈도우즈 덕택으로 DPMI가  강세를 보이고 있긴  하지만
그렇다고 해서 VCPI를 지원하지 않으면 EMM386등에서 실행되지 않는 프
로그램이 생길 수 있으므로 VCPI 또한 지원되어야 할 사항 중의 하나이
다.

6. 에러 처리 파트  도스 확장자는 보호 모드에서 생길 수 있는 에러를
처리할 수 있어야 한다.
보통의 확장자들은  중대한 에러가 생겼을 경우에 각 레지스터들
의 내용을 보여 주고 시스템이 불안정하다는 메시지를 낸다. 따라서 도
스 확장자들은 중대한  에러 발생시에도 갑작스럽게 시스템이 동작하지
않아 낭패를 보는 것을  막을 수 있다. 예를 들면 윈도우즈에서 중도에
프로그램이 더 이상 동작하지 않게 될 때 CTRL+ALT+DEL를 누르고 ENTER
를 쳐서 윈도우즈 시스템을 보호하는 것도 에러 처리 부분이 있기 때문
에 가능한 일이다.

  도스 확장자의 선택
  이제 많은 도스 확장자들  중에서 하나 선택해 보기로 하자. 여러 가
지를 고려할 수 있겠지만,  국내에 가장 많이 퍼져 있는 컴파일러 중에
서 우리  실정에 맞는 컴파일러와 확장자를  따르는 수밖에 없을 것  같
다. 도스 확장자  프로그램은 윈도우즈가 아닌 도스용 컴파일러를 기반으로 하기  때
문에 처음엔 가장 많이  퍼져 있는 볼랜드 제품을  사용해
보기로 결정했다. 하지만 문제점이 생겼다. 그 문제점들이란 바로 아래
와 같은 것이었다.

1. 준비 사항으로 볼랜드 C++ 4.02가 있어야 하고 볼랜드 파워팩은 별
   도로 구입해야 했다.(가격 12만원 추가).
2. 또한 VCPI 호스트(EMM386이나 QEMM386 등등)가 있는 경우엔 윈도우
   즈의 도스 세션에서만 실행이 가능하며, VCPI 호스트가 없으면 도스
   에서도 실행이 가능하다. (쿼터덱사의 QDPMI같은 경우엔 DPMI 0.9와
   완전 호환이 되지 않아서 충돌 가능성이 있음)
3. 생성되는 프로그램이 RTM16/32와 DPMI16/32 오버레이 파일이 PATH로
   지정되어 있어야 한다. 판매할 때 로열티를 지불하지 않아도 된다.

   초기 실행속도가 느리다.

드디어 선택의 시간이 다가왔다. 그 외에 Visual C++ 1.5같은 경우에는
Phar Lap사의 286용 도스 확장자가 포함되어 있지만 기능 제한으로 2메
가까지 메모리 사용이 가능했다. 볼랜드는 위의 단점으로 생략했다. 이

시키기 위해 DOS4GW.EXE가 꼭  필요하고 실행 후엔 특정 문자열이 출력

  DOSX의 특성
  다음은 DOSX의 특성을 보인 것이다.
1. 확장(extended)   메모리는 마치 상주(conventional) 메모리처럼 사
용이 가능하다. 이러한  특성은 특별한 고민할 필요없이(아무런 생각없
이) 메모리를 사용할 수 있는 장점이 있다.

2. 배열 선언은 사용  가능한 메모리 모두 할당이 가능하다. 예를 들면
16메가 중  남아 있는  메모리가 8메가 있다면 8메가 모두를 배열로 잡
아도 무방하다. 이 정도의 크기는

double array[2000000]; //도스  확장자를 이용한 프로그램은 64K를 초
                         과해서 사용할 수 있다

로 선언할 수 있다.  따라서 배열 선언이 많은 프로그램에선 더욱 유리
하며 메모리를 미처 사용하지  못해 잦은  디스크 accessing을  했다면
속도의 차이는 거의 3~5배까지 차이가 날 수 있다. 그리고 게임 프로그
래머들에겐 320*200*256모드 상태에서 화면 버퍼를 몇 개씩이나 만들어
두고 직접 메모리에서 비디오 메모리로 옮김으로서 더 빠른 애니메이션
을 보여줄 수 있게 된다.

3. 코드가 더욱 빠르게 실행된다. 이것은 32비트 전용 코드를 사용함으
로써 속도 면에서 16비트 컴파일러보다 2배 정도 더 빨라질 수 있는 것
이다.

4. 불합리한 메모리 접근 등은 General Protection Error를 발생하는데
이 경우에 실제 모드에서 작성한 프로그램은 시스템을 임의로 다운시키
지만, 보호 모드에서는  80386자신이 에러를 감지하고 실행 프로그램에
서 빠져나와 최악의 상태에 대비할 수 있다.
주의해야 할 사항들
  다음은 주의해야 할 사항들을 나열한 것이다.
  주로 메모리에 대한   접근과 인터럽트 처리 함수들이 바로 그것이고
그밖에 프로그래밍에서 염두해야 할 곳을 알아보기로 한다.

1. 32비트 메모리 모델에서 차이가 있는 표준 라이브러리 함수들
  bdos(), bdosx(), _chkstack(), getDS(), int86(), int86x(),
intdos(), intdosx(), peek(), poke(), segread(), write()

2. DOSX가 지원하지 못하는 표준 라이브러리 함수들
  대체적으로 디스크를 직접 Access하는 함수들과 보호 모드 작성시
near 호출만을 사용하기 때문에 Far 메모리 할당에 관련된 함수들을 지
원하지 않는다(지원할 필요가 없다).bios_disk(), dos_abs_disk_read(),
 dos_abs_disk_write()
farmalloc(), farcalloc(), farcoreleft(), farfree(), farrealloc()

3. 데이터 선언에서 주의해야 할 사항
  데이터 타DLQ 선언에 있어서 각별히 주의해야 할 곳은 int와 short의
차이이다. 16비트 방식에서 int는 2바이트, short도 2바이트였다. 하지
만 32비트 방식에서는 int가 4바이트이다. 반드시 이 부분을 염두에 두
고 프로그램을 해야 한다.

4. 치명적인 General Protection Fault의 주요 원인
  메모리에 대한 부적절한 접근(예를 들면 읽기 전용 디스크 립터에 쓰
려고 하는 경우와 널포인터에 대한 접근 등)

예제 프로그램 작성  독자들은 과연 프로그램 방식에서 어떤 차이가 있

|// 다음 예제는 메모리에 있는 임의의 값들을 quick sort한 것이다. |
|// 원래  DOS 프로그램에선 HUGE  모델을 하지 않는  한 64K를 넘길 |
|// 수 없지만,                                                   |
|// 보호  모드 프로그램에선 64K를 훨씬  뛰어넘을 수 있다. 메모리 |
|// 한도 만큼...                                                 |
|// 아래의 예제에선 정렬된 숫자 배열들을 출력하는 시간이 오래 걸 |
|// 리기 때문에 백만 개를 배열로 선언했다. 처음엔 아무 것도 동   |
|// 작하지 않는 것처럼 보이기 때문에 시스템이 다운된 것으로      |
|// 착각할 수있지만 이것은 백만 개에 대한 Sort를 하고 있는 것    |
|// 이다.                                                        |
|//                                                              |
|// 이러한  예제를 보인 것은 단지  보호 모드 프로그램의 장점을 보|
|// 기위한 것이다.                                               |
|// 컴파일 : sc -mx ex1.cpp                                      |
|#include <stdio.h>                                              |
|                                                                |
|#define NUM 1000000                                             |
|void q_numbers(long int *numbers[], long int left, long int     |
|               right);                                          |
|                                                                |
|void main(void)                                                 |
|{                                                               |
|   int i;                                                       |
|   long int *s[NUM]; // 주의해서 봐야 할 곳임                   |
|   // 보호 모드의 장점. 640KB의 메모리를 단순히 넘어 4메가를 할 |
|   // 했다                                                      |
|                                                                |
|   // 첫 번째 포인터 배열의 주소 값과 left,right 값 넘겨줌      |
|   q_numbers(s,0,NUM-1);  // Quick sort 부분이다.               |
|   printf("정렬된 숫자 배열 : \n");                             |
|   for(i=0;i<NUM;i++) printf("  %u\n",s[i]); // 정렬된 부분을 화|
|                                             // 면 출력         |
|}                                                               |
|                                                                |
|// Quick sorting 루틴                                           |
|void q_numbers(long int *numbers[], long int left, long int     |
|               right)                                           |
|{                                                               |
|   long int a=left, b=right;                                    |
|   long int *temp, *y;                                          |
|                                                                |
|   temp = numbers[(left+right)/2]; //중간 값을 계산 후 임시 저장|
|    do {                                                        |
|           // left 값과 중간 값 비교                            |
|           while((numbers[a] < temp) && a < right)              |
|                 a++; // 이미 정렬 상태면 왼쪽으로 이동         |
|           // right 값과 중간 값 비교                           |
|           while((numbers[b] > temp) && b > left)               |
|                 b--; // 이미 정렬 상태면 오른쪽으로 이동       |
|           // 비정렬 부분 교환 루틴                             |
|           if(a <= b) {                                         |
|                   y = numbers[a];                              |
|                   numbers[a] = numbers[b];                     |
|                   numbers[b] = y;                              |
|                   a++;                                         |
|                   b--;                                         |
|            }                                                   |
|      } while(a <= b);                                          |
|     // 아래의 부분에서 재귀 호출(Recursive call)형식으로 정렬함|
|      if(left < b)                                              |
|          q_numbers(numbers, left, b);                          |
|      if(a < right)                                             |
|          q_numbers(numbers, a, right);                         |
|}                                                               |

|   return;                                                      |
|}                                                               |

|void set_rgbpalette(int num,char R,char G,char B)               |
|{                                                               |
|   outp(0x3c8, num);  // 바꾸려는 색의 번호                     |
|   outp(0x3c9, R);    // 빨간 색의 값                           |

|}                                                               |

|// 32비트 처리로 화면을 버퍼로 저장하는 함수                    |
|void get_image(void *img)                                       |
|{                                                               |
|                                                                |
|long *buf = (long *)img; // 4바이트로 long 포인터 선언.         |
|// 32비트 단위로 자료를 전송하면 속도의 잇점이 있기 때문이다.   |
|                                                                |
|// 역시 주의해서 봐야할 곳으로 _x386_zeor_base_selector         |
|// (dos.h에 선언) ,                                             |
|// 그리고 Offset 자리엔 물리주소의 값을 직접 대입한다.          |
|// +,-,*,/같은 연산도 가능하다.                                 |
|long far *VID = MK_FP(_x386_zero_base_selector, 0xA0000L);      |
|   for (int i=0;i<16000;i++) buf[i] = *(VID+i);                 |
|}                                                               |
|                                                                |
|// 32비트 처리로 버퍼의 내용을 비디오 메모리로 옮기는 함수      |
|void put_image(int y, void *img)                                |
|{                                                               |
|  long *buf = (long *)img;                                      |
|  long far *VID = MK_FP(_x386_zero_base_selector, 0xA0000L);    |
|  for (int i=y*80;i<16000;i++) *(VID+i) = buf[i-y*80];          |
|}                                                               |
|                                                                |
|int main (void)                                                 |
|{                                                               |
|unsigned state;                                                 |
|int installed = 0;                                              |
|int old_mode  = set_video();                                    |
|// 비디오 메모리를 직접 다루기 위하여 해당하는 포인터를 생성한다|
|// _x386_zero_base_selector는 1MB 이하의 메모리 셀렉터이다.     |
|// 이 셀렉터와 사용할 위치의 오프셋으로 포인터를 생성할 수 있다.|
|// 이 셀렉터를 통하여 바이오스 영역이나 비디오 영역의 포인터를  |
|// 생성할 수 있다.                                              |
|// 직접적으로 포인터의 값을 지정하게 되면 General               |
|// Protection  Fault가 발생한다.                                |
|long far *VID = MK_FP(_x386_zero_base_selector, 0xA0000L);      |
|void *buff = NULL; // 메모리 할당을 위한 버퍼                   |
|                                                                |
|   set_video(0x13);   // 비디오 모드를 설정한다. 320x200x256    |
|                                                                |
|   // 팔레트를 설정한다.                                        |
|   for(int k=0;k<32;k++) set_rgbpalette(8+k, k+32, k+32, 0);    |
|   for(   k=0;k<64;k++) set_rgbpalette(40+k, 63-k, 63-k, 0);    |
|   for(   k=0;k<32;k++) set_rgbpalette(104+k, k+32, k+32, k+32);|
|   for(   k=0;k<64;k++) set_rgbpalette(136+k, 63-k, 63-k, 63-k);|
|                                                                |
|   k = 0;                                                       |
|   for(int j=0; j<200; j++)                                     |
|      for(int i=0; i<80; i++) *(VID + k++) = j<<24|j<<16|j<<8|j;|
|                                                                |
|   installed = msm_init();                                      |
|   if (installed != -1) {                                       |
|       set_video(old_mode);                                     |
|       printf ("Mouse NOT installed...\n");                     |
|       return EXIT_FAILURE;                                     |
|   }                                                            |
|   // 마우스 이벤트 발생시 호출될 사용자 정의 루틴을 설정한다.  |
|   msm_signal(0xff, &click_handler, MSTACK);                    |
|   msm_showcursor();   // 마우스 커서를 표시한다.               |
|                                                                |
|   // 마우스의 오른쪽 버튼이 눌릴 때까지 계속 루프를 돈다.      |
|   while (!(cbd.button)) continue;                              |
|                                                                |
|   buff = malloc(320*200); // 메모리를 비디오 메모리만큼 얻는다.|
|   if (buff != NULL) {                                          |
|       msm_hidecursor();                                        |
|       get_image(buff);    // 화면을 저장한다.                  |
|       for(i=0; i<16000; i++) *(VID+i) = 0L; // 화면을 소거한다.|
|       msm_showcursor();                                        |
|       cbd.button = 0;     // 마우스 이벤트 중 버튼 값을 0으로  |
|                           // 만든다.                           |
|       while (!(cbd.button)) continue;                          |
|        // 마우스 버튼 이벤트 발생을 기다린다.                  |
|       msm_hidecursor();                                        |
|       for (j=0; j<200;j++) put_image(j, buff);                 |
|       // 스크린에 다시 복구(스크롤 시킴)                       |
|       msm_showcursor();                                        |
|       cbd.button = 0;       // 마우스 버튼이 눌리기를 기다린다.|
|       while (!(cbd.button)) continue;                          |
|       free(buff);           // 버퍼를 반환한다.                |
|   }                                                            |
|   msm_hidecursor();                                            |
|   msm_signal(0, 0, MSTACK); // 이벤트 핸들러를 제거한다.       |
|   set_video(old_mode);      // 원래의 비디오 모드로 복구합니다.|
|   return EXIT_SUCCESS;                                         |
|}                                                               |

  부족하나마 설명을 끝내고  이후엔 보호 모드용 그래픽 인터페이스를
만드는 방법을 공개해 나갈 것이다. 독자들은 기존에 익숙하던 실제 모
드의 16비트 프로그래밍과  보호 모드의 32비트 프로그래밍의 차이점이
무엇인지를 잘 관찰하기 바란다. 앞으로 이에 대한 소스는 공개할 것이
다. 필자들의 목적은 보호 모드용 프로그램을 소개하는 것에 있으며 컴
파일러의 선택 역시 보호  모드용 프로그램을 하기 위해서 가장 가격대
성능비가 훌륭하다고 생각되는  컴파일러를 선택했을 뿐이다. 관심있는
독자들에겐 많은 도움이  되었기를 바란다. 그리고 정보 교환도 활발히
이루어졌으면 하는 마음도 간절하다.
